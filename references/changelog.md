**② 微信图片离线解密 + OCR —— `wxmedia.py`（新建）**
> ⚠️ **本条推翻了本技能此前写入文档的结论**：「图片拿不到字节 / 付款截图无法 OCR」**作废**。
> 根因：旧排查**看错了路径层级**（把 `xwechat_files` 父目录当账号目录，自然一个 `.dat` 都找不到）。
- 实测数据（2026-09-15）：`msg/attach/<md5(会话username)>/<YYYY-MM>/Img/` 下 **57,606 个 `.dat`、9.4 GB**，
  2026-09 单月 3,847 张。旧结论「attach 下 0 个文件」彻底作废。
- **三种加密格式**（按文件头区分）：
  | 格式 | 魔数 | 密钥 |
  |---|---|---|
  | V0 / 旧 XOR | **无魔数** | 整文件单字节 XOR |
  | V1 | `07 08 56 31 08 07` | **固定** AES key `cfcd208495d565ef` |
  | V2（本机主流） | `07 08 56 32 08 07` | **离线派生**（见下） |
- **V2 结构**：`[6B magic][4B aes_size LE][4B xor_size LE][1B 0x01][AES-128-ECB 段][16B 分隔尾][单字节 XOR 段]`；
  **总长恒等式 `file_size == 15 + aes_size + 16 + xor_size`** 是字节级精确的结构自检（用它判格式，比猜魔数靠得住）。
- **密钥离线派生**（**无需扫进程内存**）：
  - `code` = MMKV `key_<code>_*.statistic` 文件名首字段（本机 **1XXXXXXXXX**）；
  - `wxid` = 账号目录名**去掉 `_数字` 后缀**后清洗（本机 `wxid_xxxxxxxxxxxx_xxxx` → `wxid_xxxxxxxxxxxx`）；
  - `aes_key = md5(f"{code}{wxid}").hexdigest()[:16]` —— **取前 16 个 ASCII 字符直接当 16 字节密钥**，
    **不是** hex 解码（这是首次猜错的地方）；`xor_key = code & 0xFF`（本机 `0xXX`）。
  - **自证**：V1 固定 key `cfcd208495d565ef` == `md5("0")[:16]` → 同一派生式统一 V1/V2。
  - 交叉验证：`1XXXXXXXXX & 0xFF = 0xXX`，与早期用「末字节 ^ 0xD9」独立推出的值一致。
- **wxgf**：微信自研图片封装（**非 JPEG**），需调安装目录 `VoipEngine.dll` 的 `wxam_dec_wxam2pic_5` 转码。
- 命令：`doctor`（自检）/ `key`（打印派生密钥）/ `scan [--hours N] [--max N] [--ocr]` / `index`。
  产物落 `data/wechat_media/<YYYY-MM>/<md5>.jpg|png` + `data/wechat_media/index.json`。
- **端到端实测**：`scan --hours 72 --max 10 --ocr` → **扫 122 会话 / 解密 80 张 / 命中业务关键词 18 张**，
  其中读出一张**建行电子回执单全文**：
  > 付款人：智环未来（深圳）科技有限公司｜收款人：深圳市牧泰莱电路技术有限公司｜
  > **小写金额 ￥9,9XX.XX 元**｜用途：货款｜交易状态：银行受理成功
  `doctor` 全绿：数据根 ✓ / 账号 ✓ / code ✓ / `aes_key=XXXXXXXXXXXXXXXX` / `xor_key=0xXX` / 抽样解密 **5/5** / OCR 引擎可用。
- OCR 引擎：`rapidocr_onnxruntime`（**`C:\Python311` 有，managed 3.13 缺** → 跑微信命令一律用 `C:\Python311\python.exe`）。

**③ 新供应商群自动纳入监控 —— `wx_watchlist.py`（新建）**
- 业主问：「如果我后面新加了供应商的群，它会自动识别吗？比如说我在群名称上加上公司的名字，
  或者是说供应商的名字什么的，然后在 seatable 表格上也加入对应的供应商名字。」
- 答：**会** —— 只要**同时满足三个前提**：① SeaTable 里登记了该供应商名；② 群名里含这个名（
  `watch_groups` 是**子串匹配**）；③ 跑过词表刷新。
- 机制（三步）：
  1. `wx_watchlist.py refresh [--with-customers]` 从 SeaTable **供应商/客户实体**（复用
     `audit_wx_coverage.load_live()` + `collect_suppliers()`）取全量名字；
  2. `normalize()` **三层剥离**：城市前缀（`CITY_PREFIX`）→ 公司后缀（`COMP_SUFFIX`）→ 行业通用词
     （`INDUSTRY_WORDS`），再被 `STOPWORDS` 过滤、`MIN_LEN=2` 卡长度 → 产出 `entities` + `keywords`；
     写入 `data/wechat_intake/watch_auto.json`；
  3. `wechat_intake._wechat_cfg()` 变成**自动词表注入点**，把 `watch_auto.json` 的词**并进** `watch_groups`
     （`w["_auto_watch_n"]` 记录新增条数）；**三处谓词同时生效**（`_wx4_pull`、引擎B `pull`、`summary`）。
- ⚠️ **审计侧必须同步并表**：`audit_wx_coverage.load_watch_groups()` 也读 `watch_auto.json`，
  否则审计会把**已被自动纳入的群**误报成监控缺口。
- 首次实测：**43 实体 → 49 匹配词**；在真实群库中**新增覆盖 0 群**（现有手工关键词已兜住）——
  定位为**面向未来**的价值（以后加新供应商群才会体现）。词表质量健康：**单个词最多只命中 2 个群**（无过宽词）。
- CLI：`refresh [--with-customers]` / `show` / `check`。

- ★★ **业主定下看板三条口径**（原话：「生产进度看板的数据。交期如果没有填的，以历史数据推算，
  然后当前进度根据表格实际的数据，也就是说每天晚上七点收集的各类数据为准。
  然后所有的排序以及状态在计划中为优先排序。」）

  **① 没填交期的 → 用历史数据推算（覆盖 v1.8.1 的「一律不推算」）**
  旧做法是把这些计划沉到甘特图底部的灰色虚线「待补交期」条，理由是当时的业主口径
  「暂时还没有，后期手补」——**该口径 2026-09-15 作废**。
  新做法：`推算交期 = 立项日期 + 历史中位工期`，照常画在时间轴上，用
  **虚线边框 + 名称后 `≈` 号 + tooltip 写明推算依据**与真实交期区分（`est=True`）。
  - 历史基线 = **已交付计划（状态∈`STATUS_DONE`）的 `花费天数`** 分位。
    2026-09-15 实测 **n=27 · 中位 28 · p75 37 · p90 49 · min 3 · max 94 天**
    （与 `foresee.py` 的「立项→`交货时间（自动记录）`」口径**逐值吻合** 28/37/49，互为印证）。
  - 取**中位**而非 p75：交期是「典型多久能做完」，中位最无偏；p75/p90 作为保守上界写进 tooltip。
  - `hist_cycle()` 在 `compute()` 开头算一次，**全页共用**（甘特图与生产计划全表不会再各算一个数）。
  - 🔴 **推算值只读展示，绝不写回 SeaTable** —— 这些计划恰恰是因为「交期待收款后回填」的规则才留空
    （见 SKILL.md「交期以收款起算」），写回等于把业主的规则搞脏。

  **② 进度改为「表格实际数据」**
  业主：「当前进度根据表格实际的数据，也就是说每天晚上七点收集的各类数据为准」。
  → 进度不再按日期推算（那算的是「今天**该**干到哪」，不是「**实际**干到哪」），
  改读 **生产计划表「阶段」列的实测值**（`库存核对`/`备料中`/`贴片`/`组装`/`测试`/`改造中`/`已交付`…）。
  - 映射表 `STAGE_PCT`；匹配用「**最长键优先**，同长取进度更大者」——
    否则「组装料采购」会被「组装」抢走（判成 80% 而不是 45%）、「贴片料采购」会被「贴片」抢走。
  - 已交付恒 100%；阶段认不出时按 0 **低报**，绝不虚构。
  - 另把每条计划在 9 张环节表里的**实际记录数**（`plan_stages`，按 `row_id` 归属 ——
    链接列的 `display_value` 是产品名会重名，如 4 条都叫「蓝牙信标」）放进 tooltip，
    台账全空时一眼看出「进度是虚的」。

  **③ 所有排序统一「计划中」优先**
  `STATUS_ORDER` / `status_rank()`：计划中(含暂放) → 暂停 → 进行中 → 其它 → 已交付。
  甘特图、生产计划全表、项目全表都用这一套；甘特筛选档也按此顺序，并新增「计划中」按钮。
  例外：**应收口径差异明细表**仍按合同交期排（那是金额核对表，不是进度表）。
  甘特图刻度范围顺带把「今日」框进来，避免末条已交付时今日线被推出画布。

- 🔧 **顺带修掉一个静默 bug：适配器吞掉 `ctime`/`mtime` 列**
  SeaTable 的「创建时间 / 修改时间」类列（type = `ctime` / `mtime`）**不按列 key 回传**，
  而是作为**行级** `_ctime` / `_mtime` 给出（这类列的 key 恰好就是 `_ctime` / `_mtime`）。
  生产计划表的「**交货时间（自动记录）**」就是一条 **mtime 列**、`创建时间` 是 **ctime 列**。
  `adapters/seatable.py::list_rows` 早先 `if k in ("_id","_ctime","_mtime"): continue` 无条件跳过，
  于是**直连路径永远读不到这两列**（CSV 路径有，因为导出接口带真实列名）
  → `foresee.py` 用 `交货时间（自动记录）` 算历史工期分位，在直连下会**静默全空**、风险雷达失效。
  修法：只要该 key 在列定义里对应一个业务列，就照常 `key2name` 映射回列名；没定义才当纯内部时间戳丢弃。
  （`_flat_cell` 本就支持 `ctime/mtime` 类型的 ISO→`YYYY-MM-DD` 转换，无需改动。）
