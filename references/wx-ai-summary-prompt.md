# 群聊 AI 总结提示词模板

配合 `wechat_intake.py summary` 使用：脚本负责**取数和结构化**，AI（你）负责**理解和提炼**。

> 设计要点来自对 [win-wechat-summary](https://github.com/yanyan1115/win-wechat-summary) 的逆向分析。
> 该工具因硬编码 `WeChat.exe` 进程名、依赖已下架的 PyWxDump，在微信 4.x 上完全不可用；
> 但它的提示词工程值得借鉴，尤其是 map-reduce 分段合并，以及"待办带负责人"的输出结构。

---

## 输入

```bash
python wechat_intake.py summary --hours 24 --out data/wechat_intake/summary_24h.md
python wechat_intake.py summary --group "群名" --hours 168 --json --out sum.json
```

Markdown 适合人读，JSON 适合程序消费（含 `stats` 发言分布、`focus` 需关注、`messages` 全量）。

---

## 输出结构（严格按此顺序）

```
# 群聊 AI 总结：<群名>
- 时间窗口 / 原始消息数 / 发言人分布 / 生成时间

## 一句话结论          ← 不超过 2 行，说清"整体处于什么状态"
## 待办事项            ← 表格：事项 | 负责人 | 提出时间 | 状态
## 重要决策 & 共识      ← 编号列表
## 分话题要点          ← 按业务话题分组，不按时间流水账
## 风险提示            ← 表格：级别 | 事项
## ❓ 悬而未决          ← 提问后无人回复的事项
```

---

## 硬性要求（缺一不可）

1. **低活跃度直接跳过**：消息数 < 5 条时只输出「本周期群聊活跃度低，无需总结」，不要硬凑内容。

2. **待办必须带负责人**。从上下文推断，线索优先级：
   - 显式指派：「明天一早查一下」→ 被 @ 的人
   - 自告奋勇：「我来导入进去」→ 说话人自己
   - 职责归属：技术类归技术、商务类归对接人
   - 实在推断不出才写「未指定」，**不要留空**

3. **重点标出"被追问但无人回复"**。这是人工翻聊天记录最容易漏的，也是本模板最大的价值点。
   识别模式：
   - 有人在后面追问「有解决么」「查出来是什么问题了没」→ 前面的待办仍未闭环
   - 一句提问之后**连续若干条没有回应**（尤其是隔天还没人接）
   - 指派后过了时间窗仍无反馈 → 标 ⚠️ 并注明「X 天未见回复」

4. **不臆造**。每条结论都要能追溯到原文消息。推测必须写明「推测」并给出依据。
   宁可写"信息不足"，不要编造负责人、金额、时间。

5. **区分已闭环与进行中**。已完成的（如技术问题已解决）不要混进待办，放进「分话题要点」并标 ✅。

## 多群场景（默认就是这个，务必遵守）

不带 `--group` 运行时，`summary` 覆盖 `config.yaml` 的全部 `watch_groups`（实测 31 个）。
这些群业务完全不同（加工、采购、商务、项目、技术），**严禁混成一份"一句话结论"**——
「某加工厂的加工进度」和「某客户的付款条件」之间不存在可以概括的共同主语。

正确结构：**总体概览 + 按群小结**

```
# 群聊 AI 总结（多群）· <日期>

## 总体概览
3-5 句话说清：今天哪些群活跃、整体处于什么状态、最需要你关注哪件事。
（不要展开细节，那是各群小结的事）

## <群名A>（N 条）
一句话结论 → 待办（带负责人）→ 决策 → 风险

## <群名B>（N 条）
同上

## ❓ 全部悬而未决（跨群汇总）
| 群 | 事项 | 提出时间 | 负责人 |
```

排序规则：**按消息数从多到少**，不是按配置文件顺序。消息最多的群通常就是当天的主战场。

其余要求：
- **0 条消息的群直接跳过**，不要为了"全面"给每个群都写一句「今日无消息」。
- 单群消息数 < 5 条的，合并进总体概览提一句即可，不单独开章节。
- 消息数 ≥ 5 条才值得单独开章节。

> 注：`summary` 默认已把 0 条群折叠成末尾一行汇总（实测 31 群中 23 个为空，
> 折叠后省掉约 38% 篇幅）。需要完整列表时加 `--keep-empty`。

## 长对话处理（map-reduce）

单窗口消息超过 **300 条**时，直接喂全量会超 token 或导致后半段被忽略。分两步：

**第一步（map）**：按时间或话题切成若干段，每段单独生成局部摘要：

```
以下是群聊「{群名}」在 {时间段} 内的消息摘录。
请提炼：本段讨论了哪些话题、形成了什么决策、产生了哪些待办（尽量带负责人）、
有哪些提问没有得到回复。控制在 300 字内，保留具体数字、型号、金额、人名。
```

**第二步（reduce）**：把各段摘要合并成最终总结：

```
下面是同一个群聊按时间分段得到的初步摘要。
请合并成一份最终总结：去重、合并相同话题，保留重要数字、决策和待办事项。
特别注意跨段的同一件事（前面提出、后面有进展或被追问），要合并成一条完整脉络。
```

## 分类标签参考

`summary` 脚本自带的关键词标注只覆盖五类，AI 总结时应进一步按**业务话题**归并：

| 话题类型 | 典型内容 |
|---|---|
| 商务与订单 | 询价、报价、合同签订、付款条件、发货 |
| 产品质量与返修 | 客户寄回、故障定位、固件/硬件整改 |
| 技术攻关 | 方案选型、调试过程、踩坑与突破 |
| 供应链与采购 | 缺料、到货、供应商、价格变动 |
| 新项目与兼容 | 客户新需求、第三方设备兼容、样品评估 |
| 内部管理 | 人事、财务、流程规范、协作分工 |

## 与 `pull` / `alerts` 的关系

| 环节 | 职责 | 产出 |
|---|---|---|
| `pull` | 增量事件流，关键词命中即入队 | 微信事件.csv（待确认） |
| `summary` + **本模板** | 全量回溯 + AI 理解 | 待办 / 决策 / 风险 / 悬而未决 |
| `alerts` | 业务表规则检测 | alerts.json |

三者互补：`alerts` 看的是**业务数据**，`summary` 看的是**群聊里人的意图**。
群聊里「财务有点问题」这类软信号，规则引擎永远抓不到，只有 AI 总结能提炼出来。
