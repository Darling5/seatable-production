# 架构改造 · 实施清单（开工前确认用）

> 2026-10-02 · 状态：**待业主确认后才开工** · 截至目前**未改动任何数据**
> 汇总 v3（工序主线）+ v4（工序事件闭环）+ v5（阈值 + 勾选双通道）三份方案，落成可执行的批次表
> 前提：v5 的 5 条契约已拍板（见 `阈值与勾选双通道授权方案-2026-10-02.md` §0）

---

## 0. 一句话

**要改的东西分两种：一种是「加自动化、碰不到表」，可以立刻开工；另一种要「改 SeaTable 表结构」，
而当前代码只会建表、不会给已有表加列 —— 所以必须先定这件事。**

---

## 1. ★ 开工前必须先定的一件事：谁来「加列」

### 实测现状（只读核查，2026-10-02 晚）

| 能力 | 有没有 | 证据 |
|---|---|---|
| 读列定义 | ✅ 有 | `adapters/seatable.py:165` `GET /columns/` |
| **新建表** | ✅ **有** | `ensure_table()` → `POST /tables/`，还支持一次带列定义 |
| **给已有表加列** | ❌ **没有** | 全仓库无 `POST /columns/`；`add_column()` 不存在 |
| 改列名 / 改列类型 | ❌ 没有 | 同上 |
| 写行 / 更新行 / 建关联 | ✅ 有 | `update_row` / `link` / `link_append` |

### 为什么这是 blocker

v3 里最核心的三步，**每一步都是「加列」**：

```
② 项目产品  ← 给「生产计划」补 单价 / 金额 / 交付状态
③ 产品工序  ← 给「工时记录」补 状态 / 序号 / 计划开始 / 计划完成 / 是否里程碑 / 执行记录(link)
   字典     ← 给「生产工序」补 执行记录表
```

**加不了列，这三步一步都动不了。**

### 三个选项，请选一个

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）** | 我先给适配器补一个 `add_column()`（照 `ensure_table` 的写法，约 20 行），**先干跑验证**（建一列 → 确认 → 立刻删掉） | 之后所有建列都能脚本化、可重复、可审计 | 要动一次适配器代码；需先确认 token 有 schema 权限 |
| **B** | 你在 SeaTable 网页上手工建列，我给你一份「建列清单」（表 / 列名 / 类型 / 选项） | 最稳，符合「人工确认」原则，一次点完 | 后续列有变动还得手工；容易漏 |
| **C** | 混合：建列你手工点，**数据填充与工序行铺设我来跑** | 兼顾 | 需要两份清单来回对 |

> **我倾向 A**，但**A 的第一步是干跑验证**——如果 token 没有 schema 权限，`POST /columns/` 会报错，
> 那就自动退到 B，不会有任何损失。**干跑本身也是一次真实的建列，需要你点头。**

## 3. B 批：要动 SeaTable 表结构（依赖第 1 节的决定）

### B1 建新表 `工序事件`（append-only 流水）

| 项 | 内容 |
|---|---|
| 列 | `事件编号 / 日期 / 时间 / 来源群 / 发送人 / 事件类型 / 置信分 / 匹配到的记录 / 原文 / 处理状态 / 执行动作 / 处理时间`（12 列） |
| 规模 | 建表，**0 行起始** |
| 为什么单独建表 | ① 写错只多一条流水，不污染业务表 ② 规则改进了可以拿历史事件重跑 ③ 匹配失败的事件留在表里等人补，而不是被丢掉 ④ **有流水才有撤销的依据** |
| 能不能做 | ✅ **能**——`ensure_table()` 已支持一次带列建表 |
| 回退 | 删表 |

### B2 给 `生产工序` 字典加列

| 列名 | 类型 | 用途 |
|---|---|---|
| `执行记录表` | text 或 single-select | 标明这道工序由哪张表承接（如 `06 贴片` → `贴片生产记录`），**系统才能自动把记录挂到正确工序上，而不是靠人记** |
| `工期（工作日）` | number | 甘特图默认工期（字典给默认值） |
| `序号` | text | `01`~`11`，用于排序与甘特顺序 |
| `父工序` | link → `生产工序` | 把 `T` 支线（04T / 05T / 06T / 08T）归到父工序下 |

规模：15 行 × 补 4 列。回退：删列。

### B3 「`工时记录`」→ 改造为「`产品工序`」（**整个方案的核心**）

**现状实测**：`工时记录` 表**已有 10 列、0 行**，而且**双向关联已经建好了**——
`关联生产计划`（link_id=W1Q1）↔ `生产计划.工时记录`、`关联工序`（link_id=Hh3j）↔ `生产工序.工时记录`。

所以 v3 说的「骨架已对」是**真的**。已有：

| 已有列 | 类型 | 可复用为 |
|---|---|---|
| `操作人员` | text | 负责人（也可改用 `生产工序.负责人`） |
| `工时编号` | auto-number | 主键 |
| `关联生产计划` | LINK | → 项目产品 |
| `关联工序` | LINK | → 工序字典 |
| `开始时间` / `结束时间` | DATE | **实际开始 / 实际完成** |
| `实际耗时（小时）` | formula | 保留 |
| `良品数量` / `异常说明` / `备注` | number / long-text | 保留 |

需要**补 6 列**：

| 新增列 | 类型 | 用途 |
|---|---|---|
| `状态` | single-select | 未开始 / 进行中 / 已完成 / 卡住 |
| `序号` | text | 工序顺序 |
| `计划开始` / `计划完成` | date | **甘特图数据源** |
| `是否里程碑` | checkbox | 贴片完成 / 组装完成这类 0 工期节点 |
| `执行记录` | link（多态，指向 10 张表之一） | 这道工序实际落在哪一行记录上 |

> ⚠️ 一个必须先验证的技术点：SeaTable 的 link 列**只能关联一张表**，
> 而「执行记录」要指向 10 张不同的表。要么用 10 个独立 link 列（`执行记录·IC采购` / `执行记录·贴片` …），
> 要么改用「表名 + row_id」两个 text 列。**这条我建议先做一次干跑验证再定**，两个方案我都能实现。

### B4 `生产计划` → 升格为 `项目产品`

**实测发现：需要补的比原方案少。** `生产计划` 已有 45 列，其中 `生产产品` / `数量` / `版本号` / `状态`（含「已交付」）
其实**已经满足需求面的主要字段**。真正缺的只有：

| 缺什么 | 怎么办 |
|---|---|
| 单价 / 金额 | 加 2 列 number；或从 `项目.合同总价` 按产品分摊（**分摊口径要你定**） |
| 交付状态 | 可复用现有 `状态`（已含「已交付」），不必新增 |

规模：36 行。**表名是否真的改名为 `项目产品` 待你定**（改名会波及微信匹配、驾驶舱、自动化等所有读它的地方）。

## 5. 建议执行顺序

```
第 0 步  ★ 定「谁来加列」（第 1 节 A/B/C 三选一）
           └ 若选 A：先干跑验证 token 有没有 schema 权限
              ↓
第 1 批  A1 置信度改分数  →  A2 auto_approve 配置  →  A3 驾驶舱勾选框  →  A4 铁律文案
           └ 这一批不改表、不改数据，做完你就能开始「每天早上一轮勾选」的真正工作流
              ↓
第 2 批  A5 工序事件分类器（7 类）+ 群映射      ← 先只写本地 CSV，跑一两周看准确率
              ↓
第 3 批  B1 建「工序事件」表  →  B2 工序字典补列  →  B3 工时记录补 6 列
           └ B3 之前先验证「执行记录」多态关联怎么表达
              ↓
第 4 批  C1 迁产品 101 行  →  C2 铺在产工序行  →  甘特图接上
              ↓
第 5 批  C3 / C4 拆大件（408 行 + 90 行）
              ↓
第 6 批  B4 生产计划升格（表名是否改待定）
```

**为什么 A 批排最前**：它不依赖任何表结构改动，而且**做完立刻有用**——
你现在就能开始在驾驶舱上勾选，自动阈值先关着只做提示，跑稳一周再开。

## 7. 我会守的规矩（不变）

1. **任何写 SeaTable 的操作都要你逐项点头**，没授权一行不写。
2. **每批开工前先 dry-run**，把「要写什么」列成表给你确认。
3. **一条变更一条台账**（`write_ledger.csv`），带幂等键 + 读回验证。
4. **有自动就有撤销**——没有撤销的全自动不接受。
5. **改一个文件就报一个文件**，`git status` 你随时能看，回退就是一条 `git checkout`。
