# 全局业务架构升级方案（v2）

> 2026-10-02 · 状态：**待业主拍板** · 未对任何数据做改动
> v1 的「新建项目产品子表」思路被业主否掉，本版重新从**全局**出发。

---

## 一、v1 错在哪

v1 把「项目产品」当成一张**插在项目与生产计划之间的附属子表**，视野只覆盖一条线。这是错的。

正确的问题是：**整个 Base 有一类结构性缺陷，重复出现了 10 次。**

## 二、诊断：同一个缺陷，重复了 10 次

全表扫描 18 张表，用「一个 long-text 格子里有几行 Markdown 表格」做判据：

| 表 | 列 | 单据行 | **格子里塞的明细行** | 本质 |
|---|---|---|---|---|
| `IC采购记录` | 物料清单 | 71 | **215** | 一张采购单里买了 N 个物料 |
| `发货清单` | 发货内容 | 118 | **193** | 一次发货发了 N 个产品 |
| `项目` | 产品需求 | 40 | **101** | 一个项目要交付 N 个产品 |

**注意看 `发货清单.发货内容` 的表头**：

```
| 产品名称 | 产品型号 | 产品数量 | 备注 |
```

**这几乎就是「项目产品」表的字段** —— 说明**产品行的概念在业务上已经存在，只是到处被压进格子里。**

### 这个 Base 本来有很清晰的范式

它是标准的 **「主表 → 单据 → 明细」**：

```
项目 (40)
 ├ 发货清单 (118)                    ← 单据
 ├ 维修记录 (14)                     ← 单据
 └ 生产计划 (36)                     ← 单据
     ├ IC采购记录 (71)               ← 采购单据
     ├ 组装料采购记录 (38)            ← 采购单据
     ├ 成品采购记录 (28)              ← 采购单据
     ├ 贴片生产记录 (13)              ← 生产单据
     ├ 组装记录 (6)
     ├ 库存核对记录 (5)
     ├ 外壳采购记录 (5)
     ├ PCB下单记录 (3)
     ├ PCBA半成品采购记录 (7)
     └ 工时记录 (0)
```

**骨架是对的。缺的是两样东西：**

1. **「产品」没有成为实体** —— 它是这盘生意里唯一的"物"，却只以文本形式存在
2. **「单据」缺少「明细行」** —— 10 处单据把明细压在一个格子

---

## 三、关键实测：生产计划表本来就是产品粒度

这一条决定了架构走向，所以单独验证：

| 验证项 | 结果 |
|---|---|
| 36 条计划的「生产产品」文本去重 | **36 个，全部互不相同** |
| 项目内是否存在「同一产品出现在多条计划」 | **0 个项目** |
| 13 个项目 产品行数 == 计划行数 | **1:1** |

**结论：`生产计划` 表的一行 = 一个产品 = 一个批次，粒度和「产品行」完全一致。**

所以不需要再造一个平行的「项目产品」表 —— **`生产计划` 表本来就该承担产品行的角色，只是它没有需求面的字段。**

## 四、目标架构：四层，以「项目产品」为主线

```
① 主体层 ──────────────────────────────────────────────
     项目（40）              合同 / 收款 / 交期 / 客户
     （新增）供应商          主数据：24+ 个供应商现在散落在 3 张表的单选项里

② 交付项层 ───────────────────── ★ 全局主线 ────────────
     项目产品（101）         一行一个产品，贯穿需求 → 生产 → 交付
       · 需求面：产品名称 / 型号 / 数量 / 单位 / 单价 / 金额 / 交付状态
       · 生产面：生产状态 / 阶段 / 工序 / 批次号 / 计划·实际日期 / 成本
       ↑ link 到 项目

③ 单据头层 ───────────────────────────────────────────
     生产计划 · 采购单（IC/PCB/外壳/组装料/成品/PCBA）
     发货单 · 维修单 · 贴片单 · 组装单 · 库存核对单
       ↑ link 到 项目产品（而不是只挂项目）

④ 单据行层 ───────────────────── ★ 拆格子 ──────────────
     采购明细行 / 发货明细行 / 维修明细行 …
       ↑ link 到 单据头
```

**统一挂载规则（这就是"业务架构表格逻辑"）：**

| 事实类型 | 挂到哪 | 理由 |
|---|---|---|
| 合同、收款、交期、客户 | `项目` | 项目级商务事实 |
| 这个产品要多少、多少钱 | `项目产品` | 产品级商务事实 |
| 这个产品造到哪一步、成本多少 | `项目产品` | 产品级生产事实 |
| 为它买了什么物料 | 采购单 → `项目产品` | 单据头 |
| 每个物料多少钱 | 采购明细行 → 采购单 | 单据行 |
| 发了哪些产品、发了几次 | 发货明细行 → `项目产品` + 发货单 | 跨单据 |
| 修了哪个编号 | 维修明细行 → `项目产品` | 单据行 |

**一句话：产品级的事挂产品，单据级的事挂单据，绝不往格子里塞。**

## 六、SeaTable 官方能力怎么支撑这套架构

官方文档核实（2026-10-02）：

**① App Builder（通用应用）有 10 种页面类型** —— 这正是"以项目为分组、产品逐行、点进去看计划"的落地方式：

| 页面类型 | 用在哪 |
|---|---|
| **Table** | 项目产品清单，预设过滤/分组/排序/隐藏列、可设只读列 |
| **Kanban** | 按 `状态` 分组的交付看板（计划中 / 在产 / 已交付） |
| **Timeline** | 按计划·实际日期的排产时间线 |
| **Single record** | 项目详情页：一页展示合同、收款、产品行 |
| **Query** | 按项目编号/型号/序列号查 |
| **Calendar** | 发货/交期日历 |
| **Custom** | 统计看板 |
| **HTML** | 需要复杂交互时兜底 |

**关键在于**：App 的页面可以设**预过滤**，且在页面设置里可以对**关联列加过滤** —— 即「选中一个项目 → 联动只看它的产品行」，这正是官方推荐的子表体验做法（Forum 里 SeaTable 官方账号确认过）。
另外**行详情里本身就带子表视图**：打开项目一行，关联的产品行直接以列表出现在详情窗口，可增删改。

**② 自动化：4 个触发器 × 一堆动作**（`When a row is updated` / `added` / `At scheduled time` / `At scheduled time for records that match conditions`）

对我们最有用的三个动作：

- **`Add links`** —— **按条件自动建立关联**。这正是解决「存量产品↔计划对不上」的正解方向：不必一次性人工配对，可以设定规则让系统按匹配列自动挂。官方案例就是「子表首列内容一致则自动关联」。
- **`Add record to another table`** —— 立项时自动把产品行铺到 `项目产品` 表
- **`Run Python script` / `Run AI`（Extract 类）** —— **可直接用于把旧的 Markdown 格子解析成明细行**（AI 的 `Extract` 功能就是"按需求从文本列抽取信息写到结果列"）

**③ 链接公式 `lookup` / `rollup`** —— 项目表上用 rollup 自动汇总「该项目所有产品行的金额」，
产品行上用 lookup 带出「所属项目的合同交期」，**避免手工重复维护**。现在项目表的 `生产花销`、生产计划表的 9 个 `*支出` 列都已经是 link-formula，范式已经在用。

**④ 按钮列** —— 一键"发送企业微信"、一键"复制行到另一表 + 自动添加链接"。

**⑤ 版本管理与快照** —— App 和 Base 都能存快照，改造前先打快照，是官方内置的回滚手段。
