# 工序事件全自动闭环方案（v4）

> 2026-10-02 · 状态：**待业主拍板** · 未改动任何数据
> 业主目标：「从微信供应商群里自动抓取**下单、到货、发出贴片、贴片完成、贴片上线、组装上线、缺料**，要全自动完整闭环」

---

## 一、你要的 7 类事件，本质是「工序状态机的外部证据」

| 事件 | 谁发出 | 对应工序 | 现状 |
|---|---|---|---|
| 下单 | 我方 → 供应商 | 采购 | ⚠️ 只提示、不写库 |
| **到货** | 供应商 → 我方 | 采购到货 | ✅ **已实现**（`scan_arrivals`） |
| 发出贴片 | 我方 → 贴片厂 | `06 贴片` | ❌ 未实现 |
| 贴片上线 | 贴片厂 | `06 贴片` | ❌ 未实现 |
| 贴片完成 | 贴片厂 → 我方 | `06 贴片` | ❌ 未实现 |
| 组装上线 | 组装厂 | `08 组装` | ❌ 未实现 |
| 缺料 | 任意 | 阻断某道工序 | ❌ 未实现（只在关键词里） |

**7 类中 1 类已实现，6 类待建。**

而且这正好接上 v3 的工序主线：**每条事件推进一格工序，甘特图就自动更新了。**

**`scan_arrivals` 就是你要的闭环样板** —— 它的逻辑是：

> 供应商名（含别名）命中「在途采购行」（状态 ∈ 已下单 / 已付款-未到货）
> → **唯一命中 = 高置信** → 生成 `状态=已到货, 到货时间=消息日期` 的更新意图
> → 命中多条 / 只有物料词 → 中低置信 → 待人工指定

**这套「供应商 + 在途唯一 → 高置信」的模式，可以平移到其余 6 类事件。**

### 现有分类的问题

`wxwatch.CATEGORY_RULES` 现在分的是**消息性质**：交期变更 / 价格变动 / 停产通知 / 催货 / 进度 / 库存 / 其他。

实测 71 行数据（2026-09-10 ~ 09-30）：

```
进度 32 · 其他 22 · 催货 6 · 库存 5 · 价格变动 4 · 交期变更 2
```

**「其他」占 31%** —— 因为它是"消息像什么"，不是"业务发生了什么"。

**→ 要新增「工序事件」维度，与现有「消息性质」并存（不是替换）。**

## 三、闭环架构

```
① 采集   微信供应商群 ── wa_db 直读                    [已有]
② 归一   → data/微信事件.csv（71 行 / 3 周）            [已有]
③ 分类   → 消息性质（7 类，已有）+ ★工序事件（7 类，新）
④ 匹配   来源群 → 供应商/加工厂 → 在途记录候选集        [部分已有]
⑤ 写入   → ★工序事件表（append-only）+ 执行记录状态 + 产品工序进度
⑥ 反馈   风险雷达 · 企微推送                            [已有]
⑦ 撤销   台账 + 一键回滚                                [部分已有]
```

### ★ 关键设计：新增一张 append-only 的「工序事件」表

**为什么不直接改业务表：**

| 理由 | 说明 |
|---|---|
| 写错只多一条流水 | 不污染 `IC采购记录` / `贴片生产记录` 等业务表 |
| 可回溯 / 可重放 | 匹配规则改进了，可以拿历史事件重跑 |
| **不丢信息** | 匹配失败的事件留在表里等人补，而不是被丢弃 |
| **这是「全自动」能安全落地的前提** | 有流水才有撤销的依据 |

字段建议：`事件编号 / 日期 / 时间 / 来源群 / 发送人 / 事件类型 / 置信度 / 匹配到的记录 / 原文 / 处理状态 / 执行动作 / 处理时间`

## 四、匹配链（决定成败的一环）

```
来源群名  ──→  供应商 / 加工厂
      +
消息文本  ──→  型号 / 物料 / 数量
      ↓
(供应商, 型号) ──→ 在途记录候选集（状态 ∈ 已下单 / 已付款-未到货）
      ↓
唯一 → 自动写        多条 → 待确认        零条 → 待认领
```

**实测群名样本（证明这一环可行）：**

| 群名 | 可识别出 | 对应表字段 |
|---|---|---|
| `Z006-⟨本公司⟩-⟨贴片厂A⟩生产沟通群` | **⟨贴片厂A⟩** | `贴片生产记录.贴片厂` 的值正是「⟨贴片厂A⟩」 |
| `⟨客户F⟩-⟨组装厂A⟩加工沟通群` | **⟨组装厂A⟩** | `组装记录.组装厂` 的值正是「⟨组装厂A⟩」 |

**加工厂群的归属是明确的** —— 这是最难的一环，实测可行。

## 五、★ 全自动 vs 授权：这条铁律要改，必须你定

现在系统的铁律是**你自己定的**：

> 「**高置信 ≠ 授权**」—— 不带 `--grant-file` 只产「待授权清单」，**一行都不写**；
> 带授权文件才逐条经 DataService 写入（幂等键 + 读回验证 + `write_ledger.csv` 台账）。

你要「**全自动完整闭环**」，等于这条要松。**三档，请选：**

| 档 | 行为 | 适用 | 风险 |
|---|---|---|---|
| **A 保守** | 维持现状，全部人工授权 | 涉及金额/合同 | 低，但**不叫全自动** |
| **B 分级（推荐）** | **只自动写「事实时间戳」**：到货时间 / 贴片完成时间 / 组装上线时间 → 进台账 + 企微通知；**状态推进与金额仍需授权** | 大部分事件 | 中低 |
| **C 全自动** | 全部自动写（含状态推进）+ 台账 + 通知 + **一键撤销命令** | 你要的形态 | 中 |

**我建议 B**：因为「到货时间」「贴片完成时间」这类**事实时间戳**写错只影响一个日期，台账可回滚；
而「状态→已到货」会驱动 KPI、驾驶舱、风险雷达，「下单」涉及金额 —— 这些值一道人工。

**但如果你要 C，我把它做成可控的全自动**：每条变更写台账 + 企微推送变更明细（你能实时看到机器改了什么）+ `wxmatch undo <事件编号>` 一键撤销。

## 六、缺料要单独设计

「缺料」不是状态推进，是**阻断事件** —— 它让某道工序卡住：

1. 写入工序事件（类型 = 缺料）
2. 把「产品工序」对应行标记为 **卡住**
3. **触发风险雷达**（`foresee.py` 已有）
4. 企微推送（`wecom_push.py` 已有）

实测 `wxwatch.HOT_KEYWORDS` 已含 `缺料` / `缺货` / `停线` —— **已经在监控，缺的是「关联到具体产品 + 阻断工序」这一步。**

## 七、分期路线

| 期 | 内容 | 依赖 |
|---|---|---|
| **P0** | 建 `工序事件` 表（append-only）；工序事件分类器（7 类）；群 → 供应商/加工厂映射 | 无 |
| **P1** | 补齐 6 类识别：下单 / 发出贴片 / 贴片上线 / 贴片完成 / 组装上线 / 缺料 | P0 |
| **P2** | 写回：执行记录状态与日期 + **`产品工序` 进度推进（甘特图自动更新）** | v3 的 `产品工序` 层 |
| **P3** | 自动化落地（按你选的 A/B/C 档）+ 台账 + 通知 + 撤销 | 业主决策 |
| **P4** | 缺料 → 风险雷达联动 → 企微告警 | P1 |

**注意依赖**：P2 的「工序进度推进」依赖 v3 的 `产品工序` 层先立起来。
所以合理的顺序是 **v3 的 P1（立工序主线）→ 本方案 P0~P1（事件识别）→ P2（联动）**。
